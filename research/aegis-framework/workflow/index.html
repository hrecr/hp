ELEVEN STEPS · FOUR PHASES

The AEGIS Workflow

The AEGIS workflow is a proposed auditable chain from a protocol source to a trust-aware report. The public website summarizes the steps; detailed schemas remain part of the project and paper design.

PHASE A · UNDERSTAND

Turn source material into a traceable protocol representation.

01

Protocol Submission

Conceptual

Provide a protocol paper, structured description, pseudocode, message flow, or DSL.

Input
Protocol source and intended claims
Output
Submission package
02

Extraction and Normalization

Planned

Identify parties, messages, credentials, algorithms, state, and claimed properties.

Input
Submission package
Output
Protocol IR

PHASE B · MODEL

Make protocol objects, bindings, and compatibility gaps explicit.

03

IoT-PQ-AKEmin Mapping

Framework draft

Represent the protocol in a common minimal inspection model.

Input
Protocol IR
Output
AKEmin mapping
04

IoT-PQ-AKEgen Adapter

Framework draft

Construct transcripts, contexts, freshness maps, and partnering rules.

Input
AKEmin mapping
Output
AKEgen adapter
05

Compatibility Checking

Conceptual

Evaluate the protocol against structural requirements R1–R12.

Input
AKEgen adapter
Output
Compatibility findings

PHASE C · FORMALIZE

Create typed specifications and property-specific experiments.

06

DSL Generation

Planned

Generate a typed and provenance-preserving specification.

Input
Adapter and findings
Output
AEGIS DSL
07

DSL Validation

Planned

Check syntax, types, protocol flow, state, and semantic consistency.

Input
AEGIS DSL
Output
Validated model
08

Security-Game Generation

Planned

Instantiate selected AKE and IoT robustness experiments.

Input
Validated model
Output
Security games

PHASE D · VERIFY

Translate obligations, check evidence, and report each claim independently.

09

Formal Translation

Planned

Translate definitions and theorem targets to Lean or Rocq.

Input
Security games
Output
Formal projects
10

Machine Checking

Planned

Check proof terms, assumptions, placeholders, and counterexamples.

Input
Formal projects and proofs
Output
Per-theorem status
11

Final Report

Planned

Produce a precise report with evidence, limitations, and artifacts.

Input
Machine-check evidence
Output
Evidence package

WORKFLOW BOUNDARY

Visible does not mean implemented.

A step being shown on this website does not mean that its implementation is complete. Status badges distinguish framework definitions, design work, prototypes, and planned components.
