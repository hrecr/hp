FRAMEWORK · COMPATIBILITY

Structural Requirements R1–R12

The requirements make missing protocol structure explicit. They support later security definitions but do not automatically prove the selected security claims.

Conceptual specification

GROUP A · ENCODING AND TRANSCRIPT

Encoding and transcript

R1

Typed and domain-separated encoding

Protocol fields, roles, versions, and labels must have unambiguous encodings.

R2

Transcript completeness

Every value affecting acceptance, authentication, algorithm selection, or key derivation must be represented.

GROUP B · IDENTITY AND NEGOTIATION BINDING

Identity and negotiation binding

R3

Identity and peer binding

The local identity and intended peer must be tied to the session context.

R4

Credential binding

Credential identifiers used for authentication must be bound.

R5

Algorithm-suite binding

Negotiated KEM, authentication, hash, KDF, and hybrid identifiers must be bound.

R6

Role separation

Initiator and responder contexts must be distinguishable.

GROUP C · KEY ESTABLISHMENT

Key establishment

R7

Fresh contribution

The session key must depend on session-specific fresh material.

R8

Authentication binds the transcript

Authentication material must cover the relevant transcript context.

R9

Session-key derivation binds the transcript

The KDF must combine key material with the required context.

GROUP D · IOT EXECUTION SAFETY

IoT execution safety

R10

Cheap pre-authentication checks

Expose low-cost checks before expensive post-quantum operations.

R11

State-update clarity

State update timing, commit points, rollback, and recovery must be explicit.

R12

Explicit failure behavior

Failures must have clear rejection behavior and rejected sessions output no key.

RESULT VOCABULARY

Compatibility findings stay qualified.

SatisfiedPartially satisfiedViolatedUnresolvedNot applicable

A structural finding is not automatically a security proof. Each requirement is reported independently with its source evidence and limitations.
