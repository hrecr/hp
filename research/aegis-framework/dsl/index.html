PLANNED INTERMEDIATE LANGUAGE

The AEGIS DSL

The planned AEGIS DSL is a typed intermediate representation between heterogeneous protocol descriptions and formal security backends. It is intended to preserve behavior, explicit assumptions, unresolved fields, and source provenance.

Under design

WHY A DSL

A stable, inspectable boundary.

01

Normalize notation

Use consistent names across protocol families.

02

Make behavior explicit

Expose parties, values, state, and messages.

03

Separate metadata

Distinguish protocol-effective behavior from framework-only fields.

04

Support backends

Provide stable input to validators and proof exporters.

05

Preserve provenance

Trace source text to generated theorem obligations.

ILLUSTRATIVE SYNTAX

Readable structure without pretending the grammar is final.

Illustrative syntax — not a finalized grammar
protocol ExamplePQAKE {
  parties Device, Gateway
  roles Initiator, Responder
  bind { identities, credentials, algorithm_suite, transcript }
  goals { ake_secrecy, mutual_authentication, replay_resistance }
}
Expanded illustrative example — not a finalized grammar
protocol ExamplePQAKE {
  metadata { status: illustrative }
  party Device { role Initiator }
  party Gateway { role Responder }

  message m1: Device -> Gateway { kem_pk, nonce_d }
  message m2: Gateway -> Device { kem_ct, nonce_g, auth_tag }

  transcript T = [m1, m2]
  kdf_context K = bind(T, identities, algorithm_suite)
  accept Gateway when verify(auth_tag, T)

  goal ake_secrecy using freshness.default
  obligation missing_leakage_profile
}

PUBLIC NON-GOALS

The language does not invent missing security.

No silent repair

Missing protocol behavior remains missing.

No invented assumptions

Assumptions must be explicit and sourced.

No security-by-parsing

Parsing success does not imply security.

No premature grammar claim

The MVP presents illustrative syntax, not a finalized language standard.
